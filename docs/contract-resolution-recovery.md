# Declaration resolution races and recovery

The additive `2026-09-07-220000_fence_declaration_resolution` migration must precede compatible writers. Use the coordinated application admission hold and forward repair procedure; regenerate the release manifest/pins before activation. This change does not authorize deployment or a financial outcome.

A receipt keeps its original application timestamp. Its account and paid-period reads occur before waiting for the Premium account lock, and retain their actual observation time. After acquiring the lock, the declaration retains the new state separately. Mutation timestamps and visibility in this later snapshot **cannot establish commit before receipt**.

The additive `2026-09-08-010000_observe_committed_premium` migration adds `premium_period_commit_observation`. After a Premium create/extend transaction successfully commits, the same connection starts a separate observation transaction. It observes all currently visible retained operations for the affected users in deterministic operation-ID order, covering manual purchases, new periods and fixed-price automatic renewals. A database insert guard requires the original operation to be visible from a different top-level transaction and assigns `clock_timestamp()` itself, ignoring caller-supplied dates. Updates are forbidden. The timestamp is an actual **upper bound on the original commit**, never the commit time itself; a later commit of the observation record does not invalidate that already-established bound.

Only a witness strictly before receipt can establish earlier commitment within the supported clock domain. Current production uses the local PostgreSQL Unix socket and shares the application host clock. Direct Unix-socket/127.0.0.1/::1 connections use that **ordered shared-clock assumption**; tunnels/proxies to another clock and backwards clock steps are outside that assumption and must be excluded during activation/operation. Other host configurations, including an arbitrary hostname, conservatively treat timestamp order as unknown. Any configured `hostaddr` also disables clock proof, including loopback addresses, because it overrides `host` routing and can select a different fallback route. No PostgreSQL `track_commit_timestamp` or deployment-setting change is required. Original receipt time is never replaced by a database read/lock time. This is not a distributed-clock synchronization mechanism.

An absent or late witness, an operation still invisible in the first snapshot, or an operation written at/after receipt remains relevant. Declaration-specific evidence copies the witness (including its absence), clock scope, snapshot visibility, actual ledger and before/after periods. Only paid versions whose recorded new end reaches receipt are considered; old expired history does not create unbounded retrospective scheduling. Unknown ordering is explicitly described as unknown, not asserted to be an actually overlapping purchase. Existing earlier applicable boundaries remain available; the original agreement, requested date, fixed price, legitimate debit and paid access are preserved. Prompt legal/financial review is required; no refund, invalid debit or access rollback is inferred.

Observation SQL has a two-second statement timeout. Any observation failure, including its COMMIT failure, is logged **after** successful purchase COMMIT and cannot change the purchase response into an error. Process death between the two transactions leaves the purchase committed with no witness; subsequent declarations preserve uncertainty. A later purchase may truthfully observe old retained operations now, but no timestamp is backdated and immutable earlier declaration copies are not rewritten. The purchase endpoint's existing response-loss semantics are unchanged; this mechanism does not add purchase idempotency. Network/database outages have no new hard wall-clock guarantee.

`premium_transaction_observation` captures the actual top-level transaction identity of each new Premium ledger insert, including inserts made in savepoints. It does not infer identity from an earlier ledger timestamp or amount. `premium_period_changes` records every subsequent insert/extension with before/after periods, original current agreement, transaction identity/start, actual mutation time and same-transaction Premium ledger entries. Existing history remains unknown: migration creates no retrospective period mutations or ledger associations. `contract_premium_operations` copies relevant evidence independently of live account/ledger rows. No names, emails or document bytes are added to the global journal; identifiers, period dates and the actual ledger amount/time/description remain personal financial data. Declarations already retain submitted contact/details and message recipient/body. Include these additions in the restricted evidence inventory, retention/legal-hold decision, account erasure, backup/restore replay and financial review.

Witness rows cascade with their global operation on pruning/account erasure; copied provenance survives with its declaration. Their down migration refuses retained witness/copy evidence. The global journal uses the existing configured evidence cutoff, considering its mutation date and both paid ends, and cascades with account erasure. The ledger-to-transaction mapping cascades with the original ledger row. Declaration-specific copies survive those deletions and follow declaration retention: pending handling/schedules, unreviewed legacy actions and unsuperseded delivery prevent pruning. Retention policy, historic inventory and backup erasure/holds remain deployment dependencies. New operation/action evidence is immutable on update, and down migration refuses to remove retained evidence.

`contract_processing_actions` records the selected staff action, date, substantive note, effective end and the previous automatic schedule/message state. An external resolution atomically completes/supersedes its schedule and marks the old automatic resolution delivery as superseded. It never overwrites the old message's subject, body, recipient, requested reference or creation date. If an automatic resolution was attempted, a distinct `external_resolution` correction is queued to the established contact, explicitly replacing the earlier automatic end. SMTP acceptance is not inbox proof; a lost acknowledgement remains ambiguous and warrants the same correction. Replays preserve the substantive immutable message and stable Message-ID; generated transport headers need not be byte-identical.

Account, schedule and declaration locking serialize staff decisions with automatic reconciliation. A resolution send first commits its existing generation/60-second claim; then a separate transaction locks that message, rechecks generation/supersession/live lease, and holds only the message row through the existing 30-second SMTP timeout and acknowledgement. Staff waits for that bounded send before finalizing; a worker that has claimed but not started sending rechecks the terminal fence. Worker death releases its database guard. No legal receipt/effective date is shifted to the time the wait finishes. Existing dashboard submitting state persists while awaiting the API; this change adds no front-end timeout/retry. Database/network outages still require the normal operational recovery; no wall-clock bound on an unavailable database is claimed.

Old `processed_at` records do not identify which processing action was chosen. Migration labels those `legacy_unknown`, preserves their current outcome, and holds old unaccepted automatic resolution retries/schedules for explicit review. It does not guess external agreement terms or replay legacy messages. Inventory and case-specific forward repair are required for such rows; existing API completion conflicts remain in force. Monitor both these held legacy cases and new overlapping purchases promptly, including any already-sent contradictory legacy confirmation.

Focused local reproduction uses `tests/contract-review-races.py` (including the deferred-COMMIT/request-lock gap) and `tests/contract-commit-observations.py` (missing/late witnesses, failure/death, two queued purchases, guards, history, creation/renewal and conservative clock scope) with inspected `T12_STATE` and `T12_EVIDENCE_DIR`; it resets only the synthetic `t12backend` database, local cache and localhost SMTP. The separate repository tests cover a committed claim superseded before send, continued verified future scheduling, evidence erasure and forward-migration refusal. No production database, customer/payment provider or external SMTP is used.
